# Findings Qwen3.8-27B

Running list for the dense model Qwen3.8-27B (Youssofal Optimized-Speed: 4-bit g32 body, lm_head Q8/g64, MTP head bf16). Started 30 September 2026. Same ground rules as [VONDSTEN.md](VONDSTEN.md); report: [2026-09-30-qwen38](2026-09-30-qwen38.md).

Measurement setup (local, `~/Dev/laya-nl/qwen38/`): `run38.zsh <variant>` starts a fresh server per variant on port 8000 with the final-test-3 arguments for Qwen3.8 and the Bink production env, on `perf/definitief` (a5df61d0). Then `bench38.py` (4 prompts with reasoning on, server sampling, 1,200 tokens, 2 rounds; plus cold prefill of ~7K and ~22K tokens) and 2x `lus2.py` (real agent task). Hardware: M5 Pro 64 GB, turbo profile, depth 3.

| Q4 | KV quantization (`--paged-kv-quantization q8/q4`) against memory pressure at long context | 30 Sep ([kv-quantization](2026-09-30-kv-quantization.md)): not worth it. q8 decode 22.0 against 29.2 tok/s at 20K (-25%) and 9.6 against 23.6 at 60K (-59%); q4 -33% / -72%; Qwen3.6 Balance q8 -17% at 60K. The session bank does not shrink (a 60K entry is 5.4 GB with q8, 5.6 GB off) because snapshots store a bf16 mirror; live KV at 60K only -1.9 GiB, peak higher. Compiled verify does not detach (help text outdated); the cost is the quantized adapter refusing its own tail mask, so every round dequantizes the full cache. Fix on `perf/kvq8-compiled-verify` (6ce1fad4, `MTPLX_KV_QUANT_TAILMASK_ELIDE=1`, off by default): q8 25.9 tok/s at 20K and 17.3 at 60K (19.3 with the 32K compiled fence lifted); the rest is the q8 kernel being slower than bf16 NAX flash. Setting: KV off on both models |
| Q7 | Long-context depth policy: is D2 faster than D3 above some context length? | 30 Sep: no.
