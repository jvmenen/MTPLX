# FR-Spec on Qwen3.6-35B-A3B: built-in code vocabulary against a vocabulary from real Bink traffic (30 September 2026)

Question: does FR-Spec (a draft lm_head pruned to 65,536 frequency-ranked rows; the target still verifies the full 248,320-row vocabulary, so output stays exact) speed up Qwen3.6-35B-A3B, and with which vocabulary? Rank 6 in [feature-gaps](2026-09-30-feature-gaps.md); background in [VONDSTEN-QWEN38](VONDSTEN-QWEN38.md) Q2.

## Answer

- **The built-in `qwen38-code-64k` vocabulary is not worth it on Qwen3.6 for Bink:** code +5%, English +7%, but Dutch -7% (reasoning on and off). Overall +0.3%, i.e. nothing.
- **A 64K vocabulary ranked on real Bink traffic is:** code +5%, English +8%, Dutch +4% (reasoning on) and +5% (thinking off); overall **+5.4%** (87.4 to 92.1 tok/s). Agent task 2x green.
- The MoE model still gains despite the smaller draft share: the draft takes 15.9% of decode time at depth 2 with a 4-bit draft head; pruning to 26% of the rows brings that to 11.5%. That 4.4-point cut is the ceiling (~+5%) when acceptance stays equal, and the Bink vocabulary reaches it on every text type.

## Setup

- Hardware M5 Pro 64 GB, turbo profile. Worktree `perf/definitief` a5df61d0 (`~/Dev/MTPLX-definitief`), MLX 0.32.2.
- Model: `Qwen3.6-35B-A3B-MTPLX-Balance-bf16mtp-yb` (Youssofal Balance body, our BF16 MTP head), production arguments (depth 2, draft head 4-bit g64 affine, temperature 0.6, draft temperature 0.6) and the Bink production env.
- FR-Spec through the legacy lane: `MTPLX_FRSPEC_DRAFT=1 MTPLX_FRSPEC_LEGACY=1 MTPLX_FRSPEC_VOCAB=<vocab>`. The installation report shows `source: configured_draft_head`, 4-bit, `bytes_ratio 0.2639`.
- Fresh server per run on port 8000. Workload (`bench36.py`): 3 code prompts, 3 English prose prompts, 3 Dutch prose prompts (two with a Dutch knowledge-base document as source, one free advisory note), reasoning on, 1,200 tokens, server sampling; plus 2 Dutch prompts with thinking off (800 tokens). `requests_completed` checked after each run: no outside requests. Baseline 3 runs, each FR-Spec variant 2 runs, alternated. `lus2.py` (real agent task) 2x per variant.
- Scripts and vocabulary: `~/Dev/laya-nl/frspec36/` (local, not in the fork).

## Why: coverage

A token outside the pruned set cannot be proposed by the draft, so that position is always rejected. Coverage of the real Qwen3.6 output from the three baseline runs (reasoning plus answer, tokenized with the pack tokenizer; `dekking.py`):

| Output | Tokens | Built-in code 64K | Bink 64K |
|---|---|---|---|
| Code prompts (reasoning) | 10,800 | 99.3% | 99.4% |
| English prose (reasoning) | 10,800 | 97.5% | 98.8% |
| Dutch prose, reasoning on (reasoning) | 9,957 | 86.9% | 99.7% |
| Dutch prose, reasoning on (answer) | 675 | 75.1% | 99.6% |
| Dutch prose, thinking off (answer) | 3,358 | 77.5% | 99.8% |

Qwen3.6 reasons partly in Dutch on Dutch prompts, so the loss hits the reasoning as well as the answer. With 1,200 tokens the code and English prompts rarely got past the reasoning; the measurement mostly reflects reasoning text, which is what dominates Bink's token volume too.

## The Bink vocabulary

- Source: 1,363 Claude Code sessions of the Bink project (assistant text, thinking and `tool_use` inputs; tool results and blocks over 200 kB skipped): 11.1M tokens, plus all Markdown under `kennisbank/`, `agents/`, `teams/`, `projecten/`, `taken/done/` (4.1M tokens, mostly Dutch) rescaled to the same weight. The two knowledge-base documents used as benchmark input were excluded.
- 43,331 distinct IDs seen. Ranked by frequency, with the 33 special tokens (248044 to 248076) and the 256 single-byte tokens forced in: 43,452 IDs from traffic, the remaining 22,084 filled from the built-in code vocabulary as a safety net. Overlap with the built-in set: 57,480 of 65,536.
- Held-out check (10% of the session files, 939K tokens, not used for ranking): Bink 64K covers 99.92%, the built-in 93.84%. So the built-in code vocabulary misses about one token in sixteen of Bink's own text.
- Stored like the built-in: `int32`, 65,536 IDs, sorted ascending (`bink-64k.npy`), plus a ranked version for `MTPLX_FRSPEC_N` experiments (`bink-ranked.npy`). Only token IDs, no text.

## Qwen3.8-27B with the Bink vocabulary: not measured

The 3.8 agent measured the built-in vocabulary on the proper binding (`feat/frspec-qwen38-dense`, bc4618c4 and fbb146f8): code +8.6%, English +7.5%, Dutch -3.5% (reasoning on) and -12.4% (thinking off), D1 on Dutch 0.81 to 0.70. The same measurement with the Bink vocabulary (`MTPLX_FRSPEC_VOCAB=.../bink-64k.npy` on that branch) was queued but refused by the session's permission guard (running the other agent's harness); it still needs to be run. Expectation from coverage only, not measured: the two models share the tokenizer (identical `tokenizer.json`), and the Dutch coverage gap is the same (87% / 75% against 99.7%), so the Bink vocabulary should remove the Dutch regression on 3.8 while keeping the code and English gain.

## Recommendation

1. For Bink on Qwen3.6: the Bink vocabulary through the legacy lane is usable today (exact output, agent task green, +5%). Put it in production only with Jeroen's approval; it is three env variables on the server.
2. Upstream: a code-only default vocabulary costs non-English users. The PR for rank 4 (binding on the configured draft-head route) should not make the code vocabulary the family default without a multilingual acceptance check, or should ship a multilingual ranking. Our Bink file is ranked on private traffic and stays local; a public variant would need a public multilingual corpus.
3. Rank 6 in [feature-gaps](2026-09-30-feature-gaps.md) is answered: +5% on Qwen3.6, but only with a vocabulary that matches the language of the traffic.
