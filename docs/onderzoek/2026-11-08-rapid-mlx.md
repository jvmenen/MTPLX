# Finding 154: how Rapid-MLX does prompt cache (DeltaNet snapshots), the K8V4 codec, continuous batching and speculative decoding, compared with MTPLX and Splash (phase 1: code and docs read only)

Source: `raullenchai/Rapid-MLX` (Apache-2.0) at 8293099, shallow clone in `~/Dev/MTPLX/lab/rapid-mlx-analyse/rapid-mlx/` (outside `repo/` and `wt/`). Paths are relative to the clone; `rm/` stands for `rapid_mlx/`. No model loaded, no server started, nothing installed or run, production MTPLX untouched. Numbers are the maker's (own docs) or our own from findings 9, 116, 139, 147, 148 and 153; each says which. "Derived" means from a comment, doc or the shape of the code, not from reading the code path itself. Notes per topic: `~/Dev/MTPLX/lab/rapid-mlx-analyse/notities-*.md`.

Trigger: podcast Kai (8 Nov 2026), follow-up to [splash](2026-11-08-splash.md). Splash is draft plus batching in its own engine; Rapid-MLX is a Python server on top of mlx-lm with a prompt cache, a KV storage codec and its own scheduler, so it sits much closer to MTPLX than Splash does.

## Core

- **Rapid-MLX is MLX-based, like MTPLX.** It uses mlx-lm's `BatchGenerator` for continuous batching (`rm/scheduler.py:37,5508`, mlx-lm >= 0.31.3) and wraps it with its own scheduler (12,687 lines), prompt cache (`rm/memory_cache.py`, 4,922 lines), speculative runtimes (MTP, DFlash, DDTree, suffix) and tool-calling layer. The mlx-lm internals are not in the clone: how a new row joins a running batch is derived, not read.
- **The radix tree is only a lookup index.** Stored entries are whole-sequence cache copies (KV plus recurrent layers), not shared blocks (`rm/runtime/radix_index.py:1-60`, `rm/memory_cache.py:2630-2640`). A hit is a `deepcopy` of the entry. This is the opposite of Splash's content-addressed block tree.
- **GDN snapshots are references, thinned to 4 per layer.** MLX arrays are immutable, so a snapshot is a held reference to a superseded state array (`rm/hybrid_state_checkpoints.py:20-24`). At most 4 checkpoints per recurrent layer, at least 2,048 tokens apart, plus one protected "anchor" at the stable message boundary (`:37-38`, `with_checkpoint`). A divergent prompt resumes from the newest checkpoint at or below the shared prefix.
- **K8V4 is a storage codec for the prompt cache, not a live KV format.** Cache entries are compressed on store and rebuilt to FP16 on fetch (`rm/turboquant.py:759-780`); decode runs on FP16. That is a different thing from the live INT8 KV of Splash and from the q8/q4 live KV we rejected (finding 37). Their own quality evidence is cosine on synthetic tensors; there is no next-token agreement or perplexity in the repo.
- **Speculation and batching are not combined by default, and the maker found why.** A lone request uses the singleton MTP verifier; once a second request waits, the singleton yields at its next token boundary and the batch runs plain decode (`rm/scheduler.py:2895-2915,9845`, `docs/engineering/performance/2026-10-02-mtp-concurrency-m4-pro.md`). The opt-in batched MTP cohort (cap 3 lanes) loses to plain batching in the maker's measurements. This is the same conclusion as our finding 9 and the 21 Oct re-assessment, reached by a third party with a ragged-rollback implementation behind it.
- **The number Kai quotes is a short-prompt, 4-stream, single-run comparison.** Rapid-MLX 82.8 tok/s at 4 streams against LM Studio 69.7 and oMLX 75.3 on a Mac Studio M5 Max (36 GB), Qwen3.8-27B (`README.md:20-35`). Prompt length is not in the repo. The scaling is 2.18x for Rapid-MLX against 2.68x for LM Studio and 2.98x for oMLX: its lead at 4 streams is 10% over oMLX and comes from the boosted single-stream (MTP), not from better batching. It says nothing about our 20 to 60K agent turns.
- **Recommendation:** no separate phase 2 for Rapid-MLX alone; fold three Rapid-MLX measurements into the Splash phase 2 (section 9). One idea to take over as design (anchor plus stride checkpoints for the GDN boundary), one to measure cheaply (plain batching against serial for 2 streams on M5 Pro), one to read further (tool-call grammar compatible with MTP).

## 1. Prompt cache: radix tree and DeltaNet snapshots (question 1)

**Radix index.**

- `RadixPrefixIndex` is a token trie that replaces a `bisect` over sorted keys: O(prefix length) per lookup (`rm/runtime/radix_index.py:204,350`). It stores no KV; the docstring says so ("the radix only indexes token sequences", `:1-12`). Default `--prefix-cache-index radix` (`rm/scheduler.py:395`), `hash` as fallback. Persisted as `radix.index` JSON and rebuilt lazily.
- Storage stays `MemoryAwarePrefixCache`: key = full token tuple, value = the full cache (`rm/memory_cache.py`). Budget 20% of available RAM (`_DEFAULT_MEMORY_PERCENT`, `:54`), `max_entries` 1,000 (`:1264`). Disk persistence exists (`rm/disk_caches.py`, `rm/runtime/disk_kv_checkpoint.py`, checkpoints persisted too, `memory_cache.py:253`).
- No KV sharing between entries: two conversations with the same 30K system prefix each hold their own 30K KV (derived from the entry model). For Qwen3.8-27B that is ~64 KiB per token (finding 139), ~1.9 GB per 30K entry. This is where their K8V4 codec matters (section 2).

**GDN (recurrent) layers in the cache.**

- Hybrid layers are `ArraysCache`/`MambaCache` and cannot be trimmed back to a shorter prefix (`rm/memory_cache.py:1860-1900`). Default policy at store time: an entry with a non-trimmable layer is dropped (`hybrid_reuse_max_entries = 0`, `:1288,2842-2870`). With `--enable-prefix-cache` the CLI sets it to 8 for hybrid models (`_DEFAULT_HYBRID_CACHE_ENTRIES = 8`, `rm/cli.py:5260-5290`). Eviction: LRU among unprotected hybrid entries down to 8 (`_enforce_hybrid_bound_locked`, `memory_cache.py:3101-3150`); entries loaded from disk are protected and exempt.
- Fetch for a hybrid entry works only on two trim-free paths: exact match of a stored boundary, and prefix extension. An exact entry of the full N tokens is deliberately skipped, because the scheduler forwards the last prompt token again and cannot trim (`memory_cache.py:2610-2630`). Supersequence and longest-common-prefix go through `_snap_hybrid_trim` (`:1798`): KV layers are trimmed by offset, recurrent layers are restored from a checkpoint at or below the shared length (`achievable_position`, `rm/hybrid_state_checkpoints.py:374`).

**Snapshots: where, how many, how big, when dropped.**

| Question | Answer | Where |
|---|---|---|
| Boundaries | (a) every prefill chunk boundary (chunk 2,048) once at least 2,048 tokens past the previous checkpoint; (b) the message boundary (`prefix_boundary`, the stable system plus tools plus user prefix), forced; on the first cold turn it becomes the protected anchor; (c) the MLLM lane per stride | `rm/scheduler.py:6034-6090` (`_record_hybrid_checkpoints`), `:6240-6310`, `rm/mllm_batch_generator.py:3140-3160` |

| Thinning | the checkpoint with the smallest gap to its predecessor drops; the newest and the anchor never drop | `with_checkpoint` |

**What differs from our session bank and the GDN boundary.**

- Ours: session bank plus near-prefix restore, with the GDN boundary anchors on an 8,192 grid (`checkpoint_anchors.py`, `CheckpointSink`; see [rebase-2122-and-fixes](2026-10-04-rebase-2122-and-fixes.md)). Theirs: a 2,048 stride limited to 4 per layer, plus one anchor at the message boundary that thinning must keep. The idea worth reading again is the anchor: "a later request that diverges before the boundary can only resume from one of those" (`scheduler.py:6247-6256`, comment). It protects the one position that is stable across turns (system prompt plus tools) from being thinned away by newer stride samples.
- Not comparable on cost: their snapshots hold references to state arrays that stay alive per entry; ours are a grid of retained states. Neither side has published memory per snapshot for the 27B in a comparable way. The one measured recorded cost is theirs (+4% on a cold prefill).
- **Their gap, our non-gap:** their entries are full copies and a hybrid entry is bounded to 8, so memory scales with conversations. Our segmented KV and session bank were built against exactly that (findings in [segmented-kv-prototype](2026-10-07-segmented-kv-prototype.md)). I did not re-read finding 40 in VONDSTEN for this report (the row was not found by number in the open table); the comparison above uses the anchor note.

## 2. K8V4 (question 2)

- **What it is:** `--kv-cache-turboquant {v4,k8v4,none}`; default `v4` (K FP16, V 3 or 4 bit), `k8v4` opt-in (`rm/turboquant.py:5-20`, `memory_cache.py:1269-1275`). Mutually exclusive with `--kv-cache-quantization`. Based on the TurboQuant paper (arXiv 2504.19874) and arozanov/turboquant-mlx.
- **K side (8 bit):** per vector (token and head) the L2 norm in fp32, then a randomized Walsh-Hadamard rotation (signs from a fixed seed 42) and symmetric int8 with an absmax scale per vector; stored as uint8 with +128 offset, norm and scale fp32 (`turboquant_k8_encode`, `:620-668`). Head dim must be a power of two (Qwen 128/256 is fine).
- **V side (4 bit):** rotation, per group of 32 normalized to N(0,1), Lloyd-Max codebook of 16 levels, nibble-packed; scale and mean fp16 per group (`turboquant_encode`, `:479-550`).
- **Kernel:** a vendored fused Metal kernel for the K8 encode only (`rm/kernels/turboquant_fused.metal`, 230 lines; fallback to MLX ops, `:691-737`). Decode is plain MLX ops (`turboquant_k8_decode`, `:671`): every cache hit rebuilds the whole cache to FP16. Cost of that rebuild: not published.
- **Per layer, per head:** per layer only `KVCache` layers with keys are compressed; GDN layers and anything else pass through (`memory_cache.py:2192-2206`). Skip list for sliding-window (Gemma 3, gpt-oss) and MLA models (DeepSeek V3/V4, Kimi K2.5/2.6) (`turboquant.py:204-345`). Bit width is the same for all heads and layers (V auto: 3 bit at head dim >= 96, forced 4 for k8v4).
- **Their quality measurement:** unit-test cosine on tensors: K > 0.99, V > 0.93 at 4 bit (`tests/test_turboquant_k8v4.py:99-106,166-175,219-232`); fused against unfused RMSE < 1e-3 (`:347-373`). Practical claim: aider rounds passed with k8v4 (`docs/guides/gemma4-12b-18gb.md:275`). Alias flag `turboquant_tier: k8v4_verified` turns it on by default for a few models (`turboquant.py:64-110`); on `qwen3.8-27b-*` the flag is not set. **This is not a quality measurement on a real long-context agent turn.**
- **Compatibility with speculation:** the continuous MTP cohort needs BF16 KV and refuses turboquant and int4/int8 KV at startup (`docs/engineering/performance/2026-08-31-qwen35-dense-continuous-mtp.md`). K8V4 and the cohort exclude each other.
- **Candidate beside finding 37?** Not as a replacement: finding 37 was live KV (q8 and q4 slower everywhere, -25% to -72%). K8V4 changes only what sits in the stored cache. For Qwen3.8-27B only 16 of 64 layers hold KV (64 KiB per token); at 4.6x (their commentary, `turboquant.py:8-12`) that is ~14 KiB per token, about 0.6 GB instead of 2.6 GB at 40K (**estimate**). The GDN state (~153 MiB per snapshot) is not compressed. **Verdict: meten, low priority.** Worth it only if SSD size or restore time of segmented KV becomes the bottleneck; measure next-token agreement on a real 30K turn (the Splash maker's own metric: 99.2% INT8 against 99.3 to 99.45% BF16) and the rebuild time per hit.

## 3. Continuous batching on Qwen3.6/3.8 (question 3)

- **Shape:** mlx-lm `BatchGenerator`, `prefill_batch_size 8`, `completion_batch_size 32`, `max_num_seqs 256` (`rm/scheduler.py:377-381`). Decode of all running sequences is one batch step; new sequences are admitted between steps.
- **GDN state per row:** the recurrent state of a sequence is one row of the batched `ArraysCache` (derived from mlx-lm; mlx-lm not in the clone). What Rapid-MLX adds, read in docs: for the MTP cohort a per-lane snapshot of the recurrent state per verify boundary, rolled back by row-slice and concatenate (`docs/engineering/performance/2026-10-17-mtp-ragged-rollback.md`). Maker's microbenchmark, B=8, 30 recurrent and 10 KV layers (35B model): uniform rollback 0.35 ms; ragged 4.1 / 9.0 / 26.0 / 48.3 ms at 0.5K / 4K / 16K / 32K context. Qwen3.8-27B has 48 GDN layers (`2026-09-07-qwen38-mtp-gdn-verify.md`): the verify forward emits the final state and all three boundary states in one pass (45.9 to 52.3 tok/s, M3 Ultra, **maker's measurement**). That is a different answer to the GDN rollback question than Splash's tape replay: they keep boundary states, Splash keeps a tape of inputs.
- **Prefill:** in chunks of `prefill_step_size` 2,048, up to 8 prompts per prefill batch. Adaptive chunk: from a 32K-token prompt onwards the chunk shrinks to 1,024, 512 or 256 tokens when Metal memory reaches 70, 80 or 88% of the cap (`:7117-7150`). Whether a prefill chunk delays running decode steps (interleave granularity): in mlx-lm, not read. Derived: chunk boundaries are the interleave points.
- **Admission order:** `fcfs` by default. Opt-in `scheduling_policy = shortest_validated_tail` gives the next free prompt slot to the waiting request with the least uncached tail, with at most 8 deferrals per request (`:689-693,773`). A prefix-wait ("leader-wait") exists: a request sharing a long prefix with a running prefill waits for that prefill's stored state when the saved tokens exceed the extra work (`_prefill_leader_for`, `:9897-9960`, `shared_prefix_wait_tokens`, default 0 = off). That is the idea parked in the Gufo row of VONDSTEN, implemented.
- **Can a short request join during a long generation (finding 116)?** Yes in the plain batched path: the new request is prefilled and then decodes in the same batch (derived from mlx-lm's design; the singleton MTP path explicitly yields at a token boundary for it, `:2895-2915`). Its wait is the prefill chunk in flight plus its own prefill, but that is **derived, not measured**, and `shortest_validated_tail` would put such a 240-token request ahead of a long cold prompt. What it costs the running generation: it slows to the batch's per-step rate, and with speculation switched off for the whole batch.
- **Memory gate:** the scheduler admits one long prefill at a time at 32K in the maker's M3 Ultra runs ("at 32k no cohort forms on this host", `2026-10-17-mtp-cohort-m3-ultra-long-context.md`).

## 4. Speculative decoding (question 4)

- **Methods:** `mtp`, `dflash`, `ddtree`, `suffix` (explicit opt-in, only for high prompt/output overlap, `docs/suffix_decoding_eligibility.md`), prompt-lookup mentioned (`README.md:526`) (`rm/cli_parser.py:1120-1135`). For Qwen3.8-27B-4bit the MTP head is inside the model (`rapid-mlx/Qwen3.8-27B-4bit-MTP-MLX`), `mtp_continuous_batching_tier: verified`, and a DFlash drafter revision is listed in the alias.
- **MTP single stream:** K = 3 fixed (`2026-09-07-qwen38-mtp-gdn-verify.md`), 52.3 tok/s on M3 Ultra with 53.7% acceptance after the GDN-verify fusion. README lists 37.9 tok/s for the 27B on M5 Max, a different run. Not comparable with our MTP numbers without a phase 2.
- **With batching: not by default.** Continuous self-MTP and dynamic membership are default-off (`cli_parser.py:1128-1130`). Default: lone request on the singleton verifier, concurrent requests on plain batched decode, and the singleton yields at a token boundary (`2026-10-02-mtp-concurrency-m4-pro.md`).
- **Why the cohort loses (maker's measurements):** a 4-bit matmul costs roughly linearly per row from 3 to 12 rows, so a 4-lane verify of 3 rows per lane (12 rows) costs 2.8 to 4.6 single steps and delivers ~2.4 tokens per lane. M4 Pro, aggregate tok/s for 35B-A3B at 1/2/4 streams: cohort 97.7 / 111.8 / 109.6, plain batching 93.1 / 137.7 / 166.1. M3 Ultra: cohort -5% to -12% at 2 lanes, -22% at 4 lanes for short prompts, -6% at 16K. Cap raised to 3 lanes for that reason (`2026-10-17-mtp-cohort-m3-ultra-long-context.md`).
- **Is that transferable to our M5 Pro?** Only in direction. Their matmul tile saturates differently on the M4 Pro; our finding 147 shows matmul per verify forward of 66 / 91 / 93 / 104.5 ms at 4 / 9 / 13 / 17 rows on 27B, much flatter than their rows-linear curve. Their conclusion is a stronger version of our estimate (1.2 to 1.35x for two lanes), not a measurement on our hardware. The cheap measurement is plain batching against serial at 2 streams (section 9).
- **DFlash and DDTree with batching:** not established. `_max_running_sequences` restricts width only for `mtp` (`scheduler.py:9830-9870`); for other methods it returns `max_num_seqs`. Whether the dflash path is batch-correct: not found.
- **Their dependency on exactness:** byte equality with stock single-token AR is explicitly not promised; quantized near ties flip when the target forward changes from q_len 1 to >= 2 (`docs/specdecoding-validation-notes.md`). Same class as finding 29.

## 6. Tool calling (question 6)

- **Constrained decoding of the call form.** `rm/api/tool_grammar.py` turns `tools` plus `tool_choice` into an llguidance Lark grammar (triggered structural tag: free text until the `<tool_call>` special token, then only existing tool names and arguments valid against the tool's JSON Schema); `build_tool_grammar` (`:1996`), runtime mask `GrammarLogitsProcessor` (`:2261`), wired in `rm/routes/chat.py:2139`. It constrains the form of a call, never the decision whether to call. The sentinels `<tool_call>` and `</tool_call>` are single special tokens for Qwen3.5, so the grammar references them as special-token literals on both ends (`:20-45`). Optional dependency (`HAS_LLGUIDANCE`); when absent or when the builder declines, the log says `skipped:no_llguidance` or `skipped:builder_declined` and the plain parser path remains (`routes/chat.py` near `:2139-2160`).
- **Compatible with MTP.** The processor implements the speculative candidate row (`mtp_apply`, `:2625`) and snapshots the matcher state at verify boundaries (`mtp_snapshot_state`). That is a concrete answer to "does constrained decoding break draft-and-verify".
- **Reasoning.** The grammar includes a reasoning-tolerant free prefix; the maker rejected a runtime gate that switches the mask on after `</think>` because a model that emits no `</think>` would keep the mask off forever, and toggling mid-stream desyncs the matcher on multi-token boundaries (`routes/chat.py` comment, same block).
- **Parser layer.** 27 `*_tool_parser.py` files (`rm/tool_parsers/`, including the abstract base and the auto-detect parser), the Qwen3 XML parser in `qwen3coder_tool_parser.py` and a literal-safe parameter scan that keeps every byte of a value except one wrapping newline per side (`rm/tool_call_scan.py:264`, `split_marked_parameters`). Enum values that embed special tokens or XML delimiters make the schema unrepresentable and the grammar declines (`tool_grammar.py:585-680`).
- **Evidence.** A 30-scenario tool-calling set (`evals/prompts/tool_calling.json`) and a scorecard (`evals/SCORECARD.md`, M3 Ultra, 2026-03, `enable_thinking: false`): Qwen3.5-27B-4bit 83% on tools. Old, not Qwen3.8, thinking off; no tool-call number for Qwen3.8 in the repo.
- **Useful for the Bink platform?** Two things, neither in our engine: (a) the 30-scenario set as a regression test for our own tool-call path through MTPLX, which could be run without their server (**measure**, small); (b) the parser edge cases in `split_marked_parameters` and `_xml_enum_wire_unsafe` as a checklist when we see broken tool calls (**read when needed**). Constrained grammar in MTPLX itself: only worth a separate look if we measure tool-call failures; MTPLX would need an llguidance dependency (**not now**).

## 8. Ideas: take over, no, or measure

| Idea | Verdict | Reasoning |
|---|---|---|
| Protected anchor plus bounded stride checkpoints for GDN | **Take over (design)**, then measure | Their rule: thinning drops the smallest gap but never the newest or the anchor. For agent turns the system prompt plus tools is the position every later turn needs |
| Resume from a checkpoint below a divergence | **Measure** | Theirs: 7.1 to 7.5 s instead of 19.5 s on a 5.7K document. Compare with our restore on a real divergent 30K turn |
| Plain batching against serial at 2 streams, no speculation | **Measure** | The maker's counter to speculative batching; also the cheapest test of our 1.2 to 1.35x estimate |
| Yield rule: speculation off when a second request waits | **Take over (design)** | Matches finding 148 (a); what it costs a running generation is the open number |
| Shortest-tail admission | **Measure** with the jump-in prototype | A 240-token classifier call should beat a cold long prompt in the queue |
| Adaptive prefill chunk by memory pressure | **Look at** | Only relevant at >= 32K prompts; we already hold a spike reserve (see [rungs-states-and-spike-reserve](2026-10-09-rungs-states-and-spike-reserve.md)) |

## 9. Phase 2: joint, or not?

**One joint phase 2, with the Splash proposal, not a separate one for Rapid-MLX.** Reason: Rapid-MLX runs on the same stack as MTPLX (mlx, mlx-lm), so its numbers are the fairest comparison and cost one pip install, but its unique findings are three small measurements, not a different design.

Proposal (≈ 2 hours on top of the Splash afternoon, **not started**):

1. **Install** `rapid-mlx` in an isolated venv (not `prod/`, `repo/` or the platform config) and fetch `rapid-mlx/Qwen3.8-27B-4bit-MTP-MLX`. I do not install packages myself: when you give the go I create a review task for you with the exact commands. Download size not checked.
2. **GPU:** only via `~/Dev/gpu/gate.sh`, production off port 8000.
3. **Same agent turn on all three engines, one machine** (30K and 60K from the request log, greedy, order A B C C B A, cool-down): prefill s, decode tok/s, accepted per cycle; with Rapid-MLX both `--no-spec-decode` and the MTP default.
4. **Two streams at 30K:** MTPLX serial, Rapid-MLX plain batching, Rapid-MLX default (singleton yield), Splash two lanes. The Rapid-MLX arm answers "does plain batching beat serial here" without a new kernel.
5. **Short request during a long generation (finding 116):** a ~240-token call with `max_tokens 1` during a 2K-token generation at 30K on Rapid-MLX default and with `scheduling_policy shortest_validated_tail`.
6. **Divergent-prefix resume:** a 30K turn with one earlier message edited: TTFT with `RAPID_MLX_HYBRID_CHECKPOINT_MAX 4` (default) and `0` against our restore.

It answers: where the single-stream gap sits (with Splash), whether plain 2-stream batching beats serial, what a resume from a checkpoint buys against ours, and whether MTPLX tool calls pass a public set. It does not answer: quality over long agent sessions, why a difference exists (profiling), K8V4 accuracy (separate small test if the SSD question appears).
