# Finding 153: how Splash (incoai) combines DFlash2 speculative decoding with continuous batching, compared with MTPLX (phase 1: code and docs read only)

Source: `incoai/splash` main at 9124ff2 ("Serving benchmark, pressure release gate and architecture rules (#694)"), shallow clone in `~/Dev/MTPLX/lab/splash-analyse/splash/` (outside `repo/` and `wt/`). Paths below are relative to that clone. No model loaded, no server started, nothing built or run, production MTPLX untouched. Numbers are the maker's (M5 Pro) or own estimates from findings 139, 147 and 148; each says which. Lines marked "derived" come from comments, headers and docs, not from reading the kernel body.

Trigger: podcast Kai (8 Nov 2026), LM Studio 0.4 ships Splash as an experimental Mac backend. Question from Jeroen: how does Splash do in code what we rejected for Qwen3.8-27B (finding 9, the 21 Oct re-assessment, Q12)?

## Core

- **Splash is not MLX.** It is its own C++/Objective-C++ engine with its own Metal kernels, scheduler and cache, GGUF and MLX weight loading, and a per-model package (target, kernels, DFlash2 draft). A comparison with MTPLX is a comparison of engines, not of one idea.
- **Batching and speculation are one design, not two layers.** One decode step is one GPU command for 1 to 4 lanes, each with a fixed graph of 8 rows (anchor plus 7 draft proposals). Every lane keeps its own acceptance length, position, KV page table and GDN state. No cohorts, no lockstep: a lane that accepts 1 token and a lane that accepts 8 sit in the same step (`runtime/model/Runtime.cpp:3213-3217`, `runtime/metal/kernels/decode/sampling.metal:1677-1710`).
- **Per-lane state makes ragged batches cheap.** KV is paged (32-token pages) with a page table per lane, so there is no padding to the longest lane. GDN state is not rolled back: a step writes a per-lane "tape" of its rows and the next step folds only the accepted rows into the state (`runtime/metal/abi/GDN.h:44-85`, `runtime/model/QwenState.hpp:295-306`). That is a concrete answer to the "attention and GDN stay per sequence" objection in finding 139.
- **The scheduler admits per step.** A new request joins the next decode step once its prefill is done. Prefill is chunked (2048 tokens) and cut into passes so decode never waits longer than a 500 ms gap. Priority classes can interrupt a running prefill (`runtime/engine/Scheduler.cpp:344-371`, `runtime/engine/Scheduler.hpp:33-36`). This is the design behind our finding 116 (short-request jump-in), implemented in the maker's engine.
- **The limit is 4 lanes, and only short-prompt scaling is published.** Maximum batch width 4 (`runtime/metal/abi/ExecutionGeometry.h:17`). The maker's concurrency number is 170 tok/s aggregate for 4 concurrent short prompts against 74 tok/s for one (27B, M5 Pro 16-core): 2.3x, **measured by the maker**. It says nothing about 20 to 60K contexts. For our 2-agent load it does not contradict the 1.2 to 1.35x estimate in VONDSTEN (section 6, estimate).
- **The draft is the one we tested.** For 27B Splash serves `incoai/Qwen3.8-27B-DFlash2` (`install/families.py:72`), the repository of Q12, quantized to 4-bit g64 at load as we did. What differs is the engine around it (section 7).
- **The surprise is single-stream, not batching.** Splash reports 74 tok/s on one 27B stream against 16 for llama.cpp. Our Q12 run gave 35.9 to 39.0 tok/s for DFlash2 block 8 against 14.2 to 14.4 for AR, with 5.25 to 5.70 accepted per verify. Same draft, about twice the tok/s. If the maker's number holds on our machine and prompts, the gap sits in cycle cost (kernels, one fused graph per cycle) and not necessarily in acceptance. **Not comparable as it stands**: other prompts, GGUF Q4_K_M against MLX 4-bit, the maker's machine. Only a phase 2 on one machine can settle it.
- **Recommendation: phase 2 is worth it, framed as "where does the single-stream gap come from", not "do we want batching".** Section 9.

## 1. Draft verification with batching (question 1)

**Fixed graph, ragged result.**

- One DFlash cycle drafts 8 rows: the anchor plus 7 proposals (`runtime/metal/abi/ExecutionGeometry.h:6-8`). Maximum batch width is 4 (`:17`). The decode shapes are M8, M16, M24 and M32: 1 to 4 lanes of 8 rows (`runtime/engine/Scheduler.hpp:140-143`).
- "DFlash has one physical graph: anchor + seven proposal rows. A shorter output budget ... only lowers the token-exact commit count; it never changes the Metal graph shape" (`runtime/model/Runtime.cpp:3213-3217`). One command per cycle for 1 to 4 lanes: draft, verify input, target forward, selection and acceptance, commit (`Runtime.cpp:3178-3256`, derived). Only a lane with a token mask makes it three commands.
- **Acceptance per lane:** `decode_accept_dflash` runs one threadgroup per lane and writes `retained` and `accepted_count` per lane (`runtime/metal/kernels/decode/sampling.metal:1677-1710`). A lane retains `min(accepted+1, remaining, verify_rows)`, cut after the first stop token (`:1469-1473`, derived from comments). Greedy at `:1663`, sampled (`u*q < p`) at `:1487-1509`.
- Test of the ragged case: `dev/tests/engine/dflash_batch_control_metal_test.mm:63-153` gives each lane a different accepted length, remaining budget, verify rows and stop row, and checks `retained` per lane.

**Moving lanes on with different acceptance.**

- Host: per lane `states.swapDecodeParity(stateLane, retained)` and `nextLength = logicalPosition + retained` (`Runtime.cpp:2455-2470`, line numbers approximate). RoPE position per lane is `logicalPosition + row` (`Runtime.cpp:2008-2046`).
- **KV:** no rollback code found. Verify writes into scratch pages (`SPLASH_SPECULATIVE_SCRATCH_TOKENS = 7`, `ExecutionGeometry.h:12-13`). Only the logical length advances by `retained`; the next cycle overwrites the speculative suffix (`Runtime.cpp:3623-3625`, derived from the comment). The KV-write kernels themselves were not read.
- **GDN:** section 4.
- **Draft context:** per-lane `retainedCounts` and `startPositions` for the draft rings (`runtime/model/DFlashDraft.cpp:352-390`, `Runtime.cpp:2260-2277`).

**Draft length under load.**

- Not shortened or switched off for batch size. Not found (searched on accept, verify, retain, draft, speculat in the engine; `Engine.cpp` not read in full).
- What does vary is the number of rows *verified* per lane, only for a MoE target with `--verify-rows auto` (`Runtime.cpp:3724-3727`). `draft_verify_rows` (`sampling.metal:1396-1448`) ranks the proposals of all lanes by survival probability (product of acceptance probabilities, `:1415-1429`) and picks the total row count that maximizes expected tokens divided by cost at that count (`:1431-1445`). Cost per row count is a least-squares line over the last ~30 cycles, acceptance an online logistic fit refit every 64 cycles, and every 32nd cycle verifies all rows to keep the fit spread (`runtime/model/VerifyBudget.hpp:3-40`, `docs/models.md:325-396`).
- **A dense target such as Qwen3.8-27B verifies every row up to the lane's output budget** (`docs/models.md:325-331`, derived). The budget matters for A3B, not for 27B.
- The maker states the consequence: the linear-kernel plans depend on the batch width, so "a request's greedy output may change with the requests batched with it" (`docs/internals.md:593-600`), and with `--verify-rows auto` a MoE request can differ from run to run even alone (`docs/internals.md:646-650`). Same class as finding 29 and the non-reproducibility in finding 9.

## 2. KV cache per lane (question 2)

- **Paged, per lane, no padding.** Page = 32 tokens (`ExecutionGeometry.h:20`, `runtime/ops/PagedKv.hpp:101`). A page is one `SplashKvPage` u64: GPU address of the extent plus the page index in the low 14 bits (`runtime/metal/abi/KvExtent.h:23-25`). Kernels bind no KV buffer; they read through each lane's page table (`KvExtent.h:6-11`, `docs/internals.md:1183`). The verify attention kernel takes four page tables, one per lane, and per-lane params (`runtime/metal/kernels/decode/paged_attention.metal:16-19`, `params[group.z]` at `:46`, `:60`). Extents of ~128 MiB, 64 KiB aligned (`docs/internals.md:1155-1175`); pool in `runtime/engine/KvPool.hpp:119-181`.
- **KV format INT8 by default**, one fp32 scale per (token, KV head) for K and V; BF16 via `--kv-format bf16` (`PagedKv.hpp:18,153,159`, `server/serve_options.py:544-552`, `runtime/metal/kernels/common/paged_store_row.h:94`). Cost in the maker's accuracy test: 99.23 to 99.25% next-token agreement with llama.cpp on the M5 Pro against 99.30 to 99.45% for BF16 KV (`docs/performance.md`).
- **Prefix reuse over concurrent requests: yes, content-addressed.** A tree of chained hashes per full 32-token block; the key is parent block plus exact tokens plus `blockIdentity` (images, cache salt) (`runtime/engine/KvCache.hpp:44-54,98-100`). Requests hold counted references, the cache owns one prefix reference per block (`KvPool.hpp:98-100,147-148`). No copy-on-write (searched, none): shared pages are complete, immutable blocks, and a writer that recomputes the same block is moved onto the existing content (`KvCache.hpp:104-114`).
- **Waiting for a producer:** requests with a shared cold prefix can wait for a running request's planned recovery point and then enter through the normal restore path, holding no lane or pages meanwhile (`docs/internals.md:1612-1620`, `Phase::WaitingPrefix`). This is the "leader-wait for concurrent requests sharing a prefix" idea parked in the Gufo row of VONDSTEN.
- **RAM and SSD share the same block tree and recency order** (`docs/internals.md:1872`, `KvCache.hpp:44-53`, `runtime/engine/KvPageTier.hpp:27-47`). Pages are Full, Slim (only layers without window) or Index (index only, K/V on SSD) (`PagedKv.hpp:56`). Kept across restarts only with `--persistent-cache`.
- **Long-context decode attention:** split-K over history, at most 128 splits, fp32 partials and a fixed-order reduce (`ExecutionGeometry.h:31`, `runtime/metal/kernels/common/paged_attention_tile.h:17-21`); a tile of 8 rows per KV head per history split with MPP matmul (`paged_attention.metal:4-5`). Sparse attention (QSA) exists only for Qwen3.8-Flash-Next (`docs/internals.md:782-833`), not for 27B.

## 3. Scheduler (question 3)

- **A new or short request can join a running generation: yes.** Each tick replans (`runtime/engine/Engine.cpp:190`), admits per tick (`:604`, `admitQueued`) and `Scheduler::next` picks the next command (`runtime/engine/Scheduler.cpp:344-371`). `nextDecode` takes all `Phase::Decode` lanes of the highest priority and same stage, orders by priority, then longest-unserved (`lastDecodeDispatch`), then arrival, and cuts at `maximumBatchWidth` (`Scheduler.cpp:559-588`, `:647`). **No collection window**: decode runs "without waiting for more" (`Scheduler.hpp:140-143`). A lane that is still prefilling does not take part in decode.
- **Prefill is chunked and interleaved.** Chunk budget 2048 tokens (`ExecutionGeometry.h:18`, `docs/internals.md:1622-1623`). Uncontended, one command is one chunk (four at streamed weights or Index pages, `docs/internals.md:1672-1693`). With decode running, a prefill unit is cut into passes over the layers so that no unit lasts longer than the decode gap `decodeGapMilliseconds = 500` (`Scheduler.hpp:33-36`). Rows per pass follow what the last command did in that gap, floor `max(512, minimumUnitRows)` (`Scheduler.cpp:16,470`). `planPrefill` (`:497`) and `passesFor` (`:437`) were not read line by line (derived from the header and `docs/internals.md:1661-1757`).
- **Decode against prefill:** prefill and decode use different graphs and cannot share a command. Priority first; then decode runs while "decode debt" is positive (each prefill command adds `decodeShare * wallMs`, default `--decode-share 0.5`), otherwise the two kinds alternate at command boundaries (`Scheduler.cpp:344-371,733-777`, `docs/server.md:133`). Roughly half the wall time goes to decode while prefill work exists.
- **Priority:** three classes (Foreground, Normal, Background, `runtime/engine/Types.hpp:16-20`). A higher class aborts a running multi-pass prefill command (`Scheduler.hpp:68-72`, `Scheduler.cpp:336-340`, `docs/internals.md:1737-1750`). Within a class the lane with the fewest remaining rows leads, unless a request has been overtaken `maximumBatchWidth - 1 = 3` commands in a row; then it is overdue and goes first, oldest first (`Scheduler.cpp:20,399,628-641`).
- **Lanes and waiting:** 4 lanes. When all four are taken a request waits (`StateFailure::ConcurrencyLimit`, `Engine.cpp:648-655,683,744`); a request may take over the lane of a lower-priority resident, which is suspended (`Engine.cpp:640-647`, derived). Memory waits: without limit while an earlier request works, else `resource_timeout` after 30 s (`docs/performance.md`). Mask timeout 5 s (`docs/internals.md:1668-1671`).
- **Relevance for finding 116** (classifier calls of 231 to 242 tokens, max_tokens 1, waiting up to 51 s behind a 42 s generation): under this scheduler such a request is prefilled at the next command boundary and finishes within its own prefill command. Its wait would be the running command plus its own prefill, plausibly a few hundred ms at the maker's 363 tok/s prefill rate. **Derived from the design, not measured.** At priority Foreground another request's long prefill would be aborted for it.

## 4. GDN state per lane (question 4)

- **Storage:** every lane has two GDN cells (current and next), `kLaneGdnCells = 2` (`runtime/model/StateLayout.hpp:108`). Switching is metadata only: "none performs a buffer copy" (`runtime/model/QwenState.hpp:295-302`, `QwenState.cpp:433-439`). A cell holds per layer the conv state, the recurrent state (128x128 per value head, `decode/gdn.metal:206`) and auxiliary data (`QwenState.hpp:29-30`).
- **Format:** fp32 by default, BF16 via `--state-format bf16`; arithmetic always fp32, rounding at store (`runtime/ops/GDN.hpp:45`, `server/serve_options.py:555-565`, `docs/server.md:566-586`, `decode/gdn.metal:193-194`).
- **Partial acceptance without rollback ("tape replay").** Which of the 8 rows are kept is known only after the step, so the step does not write the state after its rows. It writes its rows' inputs (conv input, k, v, decay, beta) on a per-lane tape and leaves the cell at the state *before* its rows (`runtime/metal/abi/GDN.h:44-70`, `decode/gdn.metal:21-24`). The next step of that lane first folds `pendingRows` (= retained, 1 to 8) from the tape into the state and then computes its own rows (`decode/gdn.metal:186-192`, `GDN.h:72-85`; host side `QwenState.hpp:88-91,296-299`, `runtime/ops/GDN.hpp:103-115`). Rejected rows never touch the state. `snapshot` throws for a lane with pending rows, so states are published only after prefill (`QwenState.hpp:304-306`).
- **Prefix reuse of the recurrent state:** one immutable state (GDN cell plus the draft's context window) hangs on a full KV block, in RAM, on SSD or both (`runtime/engine/StateCache.hpp:134-137`, `Cache.hpp:38-53`). **Not on every token boundary.** States exist at the replay point (last whole page before the generation prompt, `docs/internals.md:1568-1570`), at junctions (branch points) and as throwaway checkpoints every 4096 tokens during long prefill (`:1622-1628`). A hit is usable up to the deepest *state*, not the deepest KV block. One state costs 153 MiB for 27B (`:1635`). A prefill chunk can stop inside itself to capture a state (`ModelBatchItem::stateCaptures`, `internals.md:1650-1655`, `runtime/ops/GDN.hpp:94-143`). Same idea as our GDN boundary grid.
- **Prefill GDN is not chunk-parallel:** the scan runs token by token in fp32 (`runtime/metal/kernels/prefill/gdn.metal:9-11`, derived from a comment). Not measured.

## 5. Kernels that are their own work (question 5)

| `prefill_gdn_prepare/scan/gate` | Prefill GDN with capture stops | `prefill/gdn.metal:193-195,306-310,333-342` | MLX-LM has GDN kernels, probably without captures |
| `draft_*`, `decode_accept_dflash`, `draft_verify_rows`, `draft_select_*` | DFlash draft attention, top-16 selector, acceptance, row budget, all on GPU | `decode/draft.metal:449-568`, `decode/sampling.metal:1059-1448,1677` | No DFlash in MTPLX (Q12 used the `z-lab/dflash` reference) |

## 6. Benchmarks they publish, and whether they cover our load (question 6)

**Published by the maker (Splash 1.0, September 2026; `README.md`, `docs/performance.md`):**

| What | Hardware | Context | Streams | Result for Qwen3.8-27B |
|---|---|---|---|---|
| Decode | M5 Pro 16-core GPU, 48 GB | short prompt (SPEED-Bench coding), 1,024 output limit, reasoning medium | 1 | 74 tok/s (2.0x the next-fastest engine) |
| Decode | same | 32K prompt | 1 | 54 tok/s (second-hand, web summary, not in the repo) |
| Prefill | same | 32K | 1 | 363 tok/s (1.2x) |
| Cached TTFT | same | 32K replay | 1 | 282 ms (7.3x) |
| Aggregate decode | same | short prompts | 4 | 170 tok/s (3.9x the next engine) |
| Aggregate | same | four concurrent 32K requests | 4 | only stated for the 35B: "3.8x" against the next engine; no absolute number in the repo |
| GGUF against llama.cpp | M5 Pro 20-core, M3 Max 40-core | SPEED-Bench coding | 1 | 74 and 92 tok/s against llama.cpp 16 and 17 (with MTP: 27 and 20) |
| Small Mac | 24 GB M6 12-core, UD-IQ3_XXS | n/a | 1 | 43.5 tok/s; context capacity 53K tokens |

Second-hand (web summary, not verified): DFlash 2 keeps 2.84x over AR at 8 concurrent requests on GSM8K against 3.43x at one.

**Own benchmark tooling** (`dev/benchmarks/serving/`, stdlib HTTP clients, `clients.py:1-30`), four scenarios:

- `churn`: 3 workers, long-output requests (1,500 tokens) whose prompt grows every round (~16.2K at round 1, 7.3K more per round), every fourth round resending the previous conversation. This looks like our agent load: growing context, resend, 3 streams.
- `ttft`: N conversations cache an ~8K prefix, then send it together with ~300-token suffixes.
- `serve1`: one request at a time, cold prompts of ~300, 2K and 14K tokens.
- `warm`: cached long prefix at several depths with short suffixes.

**Coverage of our load (agent turns of 20 to 60K, M5 Pro, 2 agents):**

- The published batching number is for **short prompts**. At 20 to 60K the attention and KV part grows per lane and is not shared between lanes (finding 139: 4.9 ms per 10K context per round, 36% of a round at 100K). So 170/74 = 2.3x at 4 short streams is an upper bound, not a prediction.
- Check with our own numbers (**estimate**): matmul per verify forward is 66 ms at 4 rows and 104.5 ms at 17 rows (finding 147). Two lanes of 8 to 9 rows batched are ~17 rows: ~105 ms against 2 x 91 = 182 ms serial, 1.7x on the matmul share only. Add per-lane attention (~20 ms per lane at 40K), GDN and draft, and 1.2 to 1.35x total stays plausible. The maker's 2.3x at 4 streams (36 rows; we have no matmul number above 25 rows) is consistent with that, not with much more.
- The 3.8x for the 35B at four concurrent 32K requests is a ratio against another engine, not a scaling factor over one stream.
- Not published: M5 Pro with 2 streams at 20 to 60K on 27B, TTFT of a short request during a long generation, accuracy of INT8 KV with DFlash at 60K. The `churn` scenario would cover our load once pointed at both servers.
- Cost of the same design on small machines (`docs/performance.md`): a 16 GiB SSD cache wrote 26 GB in 30 minutes (~50 GB per hour) with six clients on the 24 GB M6. The repo advises `--language-only` for coding agents (Claude Code's own prompt is ~33K and 64K compacted repeatedly).

## 7. DFlash 2 draft for 27B, and what differs from Q12 (question 7)

- **Same draft.** `incoai/Qwen3.8-27B-DFlash2` (`install/families.py:72`). In Q12 we used revision 015e795 of that repository with `z-lab/dflash` at 07ebd93, quantized to 4-bit g64 at load (`2026-10-02-qwen38-speed-options.md:48`). Splash quantizes the draft's BF16 projections into af4g64 planes, "4 bits in groups of 64 as MLX's affine quantization rounds them" (`docs/models.md:392-394`). Which revision Splash follows is not pinned: the installer follows the repository's default branch (`docs/models.md:292-301`). Whether it is still 015e795: not checked.
- **Draft shape fixed by the kernels:** 32 query and 8 KV heads of 128, selector rank 256 with 16 candidates, a 2048-token window, a block of at least 8 rows of which a cycle drafts the first (`docs/models.md:310-316`, `runtime/metal/abi/DraftAttention.h:12`). The draft reads outputs of the target layers named by `dflash_config.target_layer_ids` (at most 8); in Q12 we noted five tapped layers.
- **What differs from what we tested:**
  1. **Block:** always the full 8 rows (anchor + 7). We tested block 8 (5.25 to 5.70 accepted per verify) and block 5 (3.82 to 4.16), and block 5 was faster in our implementation. In Splash the graph shape is fixed, so the trade-off between rows and cost is not made by shortening the block. The maker: "A fixed shorter block would do worse: in agentic use about one cycle in six accepts all seven proposals and one in five accepts none" (`docs/models.md:369-371`).
  2. **Cycle cost:** draft, verify, accept and commit in one GPU command, with selector, accept and row-budget kernels on the GPU (`Runtime.cpp:3178-3256`). In Q12 we ran the reference implementation around MLX (not read again for this report), and listed GDN rollback on partial accept as an integration cost.
  3. **GDN on partial accept:** tape replay (section 4).
  4. **No context-copy or prompt lookup in Splash:** searched docs and headers, nothing found. That is what made MTP plus context-copy beat DFlash2 on edit-shaped work in Q12 (47.2 against 42.7 tok/s). Splash's 74 tok/s is on SPEED-Bench coding prompts, not on editing text that is already in context.
  5. **Sampling:** acceptance for sampled lanes keeps the exact target distribution (`docs/models.md:344-346`). We did not test sampling in Q12.
  6. **Target:** their 74 tok/s uses GGUF UD-Q4_K_M kernels (README); we used MLX 4-bit g64 on the production body. Splash can also load MLX 4-bit targets into the GGUF weight layout and measured within 0.5% of its own packages (`docs/performance.md`).
- **Not answered in phase 1:** accepted tokens per cycle for 27B on Splash are not published in the repo (no hit in the docs). So we cannot say whether their acceptance is above our 5.25 to 5.70 or whether the speed comes wholly from cycle cost.

## 8. Ideas: take over, no, or measure

| Idea | Verdict | Reasoning |
|---|---|---|
| Short-request jump-in with priority and a bounded wait: admission at the next command boundary, long prefill in passes, higher priority aborts a running prefill | **Take over (design)**, measure in the prototype of finding 148 (a) | Splash shows the shape: admission per command, priority classes, decode share 0.5, decode gap 500 ms. For us the 1-token classifier case is simpler: drain between decode rounds. To measure: our real resume cost (assumed 0.3 to 1 s in finding 148) |
| Fixed-shape fused cycle (draft, verify, accept, commit in one command) | **Measure** | Likely source of the 74 against our 36 to 39 tok/s on the same draft. Overlaps with `lab/compiled-verify` and `lab/cv6`: first compare what those already bought |
| GDN tape replay (write rows to a tape, fold only retained rows next step) | **Measure** | Look at how MTPLX handles GDN after partial acceptance and what that costs per round. It is also the prerequisite for ragged lanes. Not studied in phase 1 |
| Ragged multi-lane verify (own page table per lane, 8 rows per lane, per-lane acceptance) | **No for now** | Needs a paged or segmented per-lane attention kernel, a compiled verify per lane count, session bank and context-copy per lane, and gives bitwise differences with solo (finding 9, 21 Oct re-assessment). Gain for two agents at 20 to 60K stays ~1.2 to 1.35x (estimate). Revisit only if phase 2 shows an aggregate gain well above that |
| INT8 KV cache | **Measure** | Already option 3 in finding 139. Maker: ~0.1 point of next-token agreement lost against BF16 for 27B. Our own KV q8/q4 test (`2026-09-30-kv-quantization.md`) was slower everywhere (-25% to -72%); Splash dequantizes inside the attention kernel (`paged_store_row.h:94`, kernel bodies not read) |
| Content-addressed block tree shared between concurrent requests | **No** | We have the session bank and near-prefix restore; parallel agents rarely share a cold prefix. The leader-wait variant stays parked (Gufo row) |
| Verify-row budget (cost and acceptance model per lane count) | **No for 27B** | Dense target: Splash itself verifies every row. Possibly relevant for A3B (maker: 0.9 to 8.7% faster on an M5 Max), but A3B is not our agent model |
| Draft sliding window of 2048 and draft rings per lane | **No** | Part of DFlash; we are not integrating the draft |
| DFlash2 for 27B again | **No change to Q12**; re-open only if the fused cycle proves to be the whole gap | Same draft; the gap is engine, not model |
| ANE prefill (private API) | **No** | Private API, fragile, and no like-for-like prefill number exists |
| Sparse attention (QSA) | **No** | Only Qwen3.8-Flash-Next |

## 9. Phase 2: worth it?

**Yes, one afternoon, framed as "where does the single-stream gap come from", not "do we want batching".** The reason is one number: the same draft at about twice the tok/s. If that holds on our machine, it is worth more than the 1.2 to 1.35x from two-lane batching, and it changes what GPU time goes to.

Proposal (≈ 3 hours including download, not started):

1. **Install** the Splash release in an isolated place (brew or the app; no change to `prod/`, `repo/` or the Bink config). The 27B model `unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_M` is roughly 16 to 17 GB (derived from the quant size, not checked). Needs Jeroen's go for the install and the download; I do not install packages myself.
2. **GPU:** only via `~/Dev/gpu/gate.sh` and with production off port 8000 (README rule 5).
3. **Same agent prompt, one machine:** one real agent turn (30K and 60K, replayed from the request log, greedy) on both engines, order A B B A, cool-down between runs. Record prefill s, decode tok/s, accepted tokens per cycle (MTPLX log; Splash `/status` speculation counts, `docs/api.md` "Output limits and streaming"), power and thermal state.
4. **Two streams:** the same turn twice at the same time at 30K; aggregate and per-stream tok/s on both engines (MTPLX serial as reference; `mtp_batch` does not apply to 27B).
5. **Short request during a long generation** (finding 116): a classifier-like call of ~240 tokens with max_tokens 1 during a 2K-token generation at 30K; TTFT on both.
6. **Their churn client** (`dev/benchmarks/serving/clients.py`, stdlib, OpenAI API) as a ready-made 3-stream growing-context load. Whether it runs against MTPLX unchanged is not checked.
7. **Output check:** greedy output of an edit-shaped prompt against MTPLX (the context-copy case where DFlash2 was behind in Q12).

It answers: (a) single-stream speed on our prompts, (b) whether 2 streams at 30K give ~1.3x or clearly more, (c) whether the jump-in works as the design suggests, (d) whether Splash's accepted-per-cycle is above our Q12 figures.

It does not answer: why (that needs profiling, a separate phase 3), quality over long agent sessions, and tool-call fidelity (Splash has its own chat format and tool parsing, `server/chat_format.py`).
