## What changed upstream that matters

- #4416 (head-dim-256 prefill with array mask runs the fused NAX kernel) rewrote the very condition our minq patch edits. It now reads `q_len >= 1024 && D == 256 && (do_causal || has_arr_mask)` on NAX, plus a new non-NAX clause (fp16/bf16, causal, q_len >= 2048, q_len == kv_len).
- #4380/#4431 (`sdpa_vector_2pass_1_gqa` for GQA 12 and 16, batch-offset fix) touch decode only (q_len <= 8). They do not interact with minq (which only applies to q_len > 8). They are the likely reason long-context decode numerics shift (see e2e).
- Other SDPA changes in the range: D256 and D512 memory reductions (#4505, #4487), D96/V64 (#4499), D512 vector kernel (#4459), NAX for long unmasked D72/D80 (#4455), a renamed and generalised head-dim split NAX kernel (WN 2 or 4). qmm: global-scale qmm, dispatch fix for non-transposed affine qmm (#4392), gather_qmm work; none conflicted with the tile patch.

## Conflicts

1. minq patch: one textual conflict in `scaled_dot_product_attention.cpp`. Resolved by keeping upstream's new condition and replacing only the constant 1024 with `d256_min_q()`. Consequence: the threshold now also applies to array-mask calls (upstream #4416 only enabled them from 1024 rows). With `MLX_SDPA_D256_MINQ=64`, array-mask head-dim-256 calls with 64..1023 query rows now also take the fused kernel. Production uses causal masks; the numerics test below (causal) passes at 64. Array-mask at short q was not separately validated.
2. qmm tile patch: applied clean.
3. sdpa-lse: conflict in `mlx/fast.h` (both additions kept); three build/test fixes needed: (a) `d_half` renamed `d_group` upstream in the dsplit kernel, (b) new padded D72/D80 NAX call needed the new `lse` argument, (c) the lse commit's non-NAX threadgroup-memory check rejected D512 on NAX (test_sdpa_full_head_dim_512_nax failed); D512 added to the NAX list. All folded into the single lse commit.

## Recommendation

Prefill is unchanged (within 0.5%), decode unchanged at 8K, memory unchanged. The only difference is a greedy divergence at 50K, most likely upstream's changed decode kernels (#4380/#4431) shifting floating-point order, not a defect. Switching gains nothing measurable and the fork policy says to switch only when something is gained or needed; but staying on 0.32.2 means falling behind (bug fixes, D256/D512 memory work). Suggested: switch is safe (nothing regressed), do it when convenient; if token-exactness against earlier 50K outputs matters (e.g. cache-hit comparisons across builds), expect one-off differences. Before the switch, cheap extra check if wanted: a long real conversation with a human glance at output quality.

## MTPLX suite on pkg-combo-0323: the 8 failures explained (9 October)

The full MTPLX suite on `prod` passes with pkg-combo (0.32.2) and fails 8 tests with pkg-combo-0323. None is a regression for the production models (Qwen3.8-27B dense, Qwen3.6-35B-A3B MoE, Apodex mini); five failures are in code for the Qwen4 / Flash-Next family (125B-A6B), which is not in the production config.

| Test(s) | Cause | Class | Touches production models |
|---|---|---|---|
| `hc_verify_read::test_the_tables_are_the_stock_lowerings_at_every_input` | The test decides "is this 0.32.2" with `importlib.metadata.version("mlx")` (the venv wheel, 0.32.2) instead of the loaded build, so it expects the two sigmoid lowerings to differ, which they no longer do in 0.32.3 (the test's own comment says so). Table check itself passes. | (a) test reads the wrong version | no (hyper-connection, Flash-Next) |
| `moe_sorted_gather` x3 (rows 34040, 40950, 32770) | Build marker `0.32.3.combo-lse`: the guard's pre-release regex reads `.combo` as a `c` pre-release, so it treats the build as older than 0.32.3 and engages. The test then expects the stock call to drop rows, but 0.32.3 is correct. Against an fp32 reference: 0.32.2 max relative error 0.70 (32,770 rows) and 0.94 (40,950 rows), 0.32.3 0.0033 and 0.0036. With marker `0.32.3.lse` the guard is off and the tests pass. | (a)/(c) marker artifact, plus a genuine upstream fix (#3922) | A3B MoE: yes, via the guard; it only added harmless padding; the kernel itself is better on 0.32.3 |
| `qwen4_m4_routed_glu::test_paired_routed_glu_is_bit_exact_at_physical_m4_shape` | Test demands bit equality between MTPLX's custom kernel and stock `gather_qmm`. In 0.32.3 stock `gather_qmm` changed (#4572 and related): 0.04% of the values differ in the last bit. Error against an fp32 reference is identical for both (max relative 0.0076, mean 0.00239 on both builds, kernel and stock). | (a) test over-strict | no (Flash-Next only) |
| `qwen4_route_kernel` x2 (`topk_sum_accumulates_in_bf16_in_slot_order`, `slot_order_changes_the_renormalised_scores`) | These run on the CPU stream. Since #4387 CPU `sum` widens bf16 to fp32 (0.32.3: matches fp32 in 100% of values; 0.32.2: matches the bf16 add-by-add loop in 100%). The GPU `sum` is unchanged and bit-identical between 0.32.2 and 0.32.3 (checked for 40 shapes). The Metal rule the kernel copies has not changed. | (a) CPU-reference behaviour changed upstream | no (Flash-Next router only) |
| `release_pins::installed_mlx_is_the_pinned_version` | Pin in `pyproject.toml` is 0.32.2. | (c) pin | all, formally |

Proposed test changes (not applied in MTPLX-prod):
1. `tests/test_hc_verify_read.py` (around line 170): drop `from importlib.metadata import version` and use `if mx.__version__.startswith("0.32.2"):`. Verified on a scratch copy.
2. Name the MLX build `0.32.3.lse` (or `0.32.3+combo.lse`); or harden `_PRE_RELEASE` in `mtplx/moe_sorted_gather.py` so a word such as `combo` is not read as `c`. `pkg-combo-0323` was rebuilt with marker `0.32.3.lse` for this check (version string only).
